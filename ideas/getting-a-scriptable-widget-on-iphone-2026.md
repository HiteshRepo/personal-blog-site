# Getting a Custom Widget onto an iPhone in 2026 is Surprisingly Hard

- type: war-story
- tags: ios, scriptable, shortcuts, iphone, homelab, debugging

- The deceptively simple goal: get a JavaScript widget running on an iPhone home screen that polls a local HTTP endpoint — ended up being a 2-hour debugging session across 4 separate blockers
- Blocker 1 — unsigned shortcuts: tried generating a `.shortcut` plist file programmatically with Python's `plistlib` to auto-import the iOS Shortcut for push data collection; iOS 15.4+ removed the "Allow Untrusted Shortcuts" toggle entirely; files signed outside Apple's toolchain are blocked with no workaround
- The `.shortcut` plist format is undocumented: reverse-engineered the structure (WFWorkflowActions array, UUID-keyed magic variable references, WFTextTokenString serialization type, Aggrandizements for type coercion) — generated a syntactically valid file that iOS still refused to import
- Fix for shortcuts: just walk the user through 3 manual actions in the Shortcuts app — Get Battery Level, Get Network Details (WiFi Name), Get Contents of URL (POST) — takes 3 minutes and is more reliable than any file-based import
- `wifi_connected bool` vs `wifi_name string`: the Shortcuts "Get Network Details → Network Name" action returns a string (the SSID), not a boolean; Go's JSON decoder is strict and returns `cannot unmarshal string into bool`; the fix was to change the Go struct field from `*bool` to `*string` and just store the network name
- Blocker 2 — macOS firewall blocking the HTTP server: tried serving widget.js from a Python `http.server` on the Mac; iPhone couldn't reach it; macOS firewall blocks incoming connections even with `ufw inactive`; eventually confirmed by checking `netstat` (port was bound to `*.8888`) but iOS still timed out
- Blocker 3 — MetalLB IP not reachable from WiFi: `192.168.29.201` (MetalLB LoadBalancer) is reachable from the Mac (wired or same switch) but not from the iPhone (WiFi); MetalLB L2 ARP announcements don't always propagate to wireless segments depending on router configuration; fix is to use the NodePort (`192.168.29.146:31376`) via the Lenovo's actual IP which the iPhone can always reach
- Blocker 4 — base64 corruption when embedding files in Go source: tried encoding widget.js as a base64 constant in `main.go` and decoding at request time; the base64 string got silently corrupted during copy-paste into the editor (a space appeared mid-string, turning "async" into "anync"); `//go:embed widget.js` reads the actual file at compile time and is the right solution — zero corruption risk
- The working distribution strategy: serve widget.js directly from the status-api binary via `/widget.js` endpoint using `//go:embed`; iPhone opens `http://192.168.29.146:31376/widget.js` in Safari, selects all, copies into Scriptable — no AirDrop, no file server, no signing required
- Scriptable itself works fine once the code is in: `args.widgetParameter` for runtime URL override, `config.runsInWidget` to switch between widget rendering and full-page UITable detail view, `Request.loadJSON()` for fetch — all behave as documented
- Key lesson: for local-network-only tools, skip HTTPS entirely and use the host's real LAN IP + NodePort — avoids self-signed cert issues in Scriptable, Safari, and Python `requests` without any certificate trust setup
- iOS widget auto-refresh is controlled by Scriptable's background execution model (≈5 minutes minimum) — the widget can't force a refresh; for live monitoring, tap the widget to open the full-page detail screen which fetches on demand
